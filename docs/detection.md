# Detection Rules

What SIB detects out of the box, how the rules map to MITRE ATT&CK, which rule packs are optional, and how to add your own.

## Rule packs

The rules live in `detection/config/rules/`. Falco loads the files listed under `rules_files` in `detection/config/falco.yaml.template`.

| File | Loaded | Contents |
|------|--------|----------|
| `falco_rules.yaml` | Yes | A selection of the upstream Falco rules (15 rules) and the shared macros the other packs use |
| `custom_rules.yaml` | Yes | SIB's own rules (60 rules), mapped to MITRE ATT&CK |
| `falco-incubating_rules.yaml`, `falco-sandbox_rules.yaml` | Yes | Empty placeholders for your own incubating or experimental rules |
| `cloud_rules.yaml` | Opt-in | AWS/GCP/Azure: metadata service, credentials, cloud CLIs (6 rules) |
| `webserver_rules.yaml` | Opt-in | Nginx, Apache, PHP-FPM: shells and downloads from web processes (6 rules) |
| `coding_agent_rules.yaml` | Opt-in | Claude Code, Codex and HIB hosts: credential reads and persistence writes by coding agents (5 rules). See [HIB Integration](hib-integration.md). |
| `falco_threatintel_rules.yaml` | Opt-in | Generated by `make update-threatintel`. See [Threat Intelligence](threat-intel.md). |

### Enabling an opt-in pack

On the SIB server, uncomment the pack's line under `rules_files` in `detection/config/falco.yaml.template`, then run `make install-detection` (`falco.yaml` is generated from the template). On fleet hosts, add the file to the host's `falco_custom_rules` in the Ansible inventory and run `make update-rules` or `make deploy-fleet`. [HIB Integration](hib-integration.md) shows both for `coding_agent_rules.yaml`.

Check that all packs load together with `make test-rules`.

## What gets detected

| Category | Examples |
|----------|----------|
| **Credential access** | Reading `/etc/shadow`, SSH private keys, AWS credentials, Kubernetes service-account tokens |
| **Container security** | Shells in containers, Docker socket access, `nsenter` and mount-based escapes, container runtimes inside containers |
| **File integrity** | Writes below `/etc` and binary directories, sudoers and password file changes |
| **Process anomalies** | Shells from untrusted binaries, binaries run from `/dev/shm` or `/proc`, `memfd` execution, process masquerading |
| **Persistence** | Crontab changes, new systemd services, webshell indicators, netcat listeners |
| **Defense evasion** | Log and history tampering, timestomping, kernel module loading, disabling security tools |
| **Discovery** | System, network, process and account enumeration, cloud metadata access |
| **Lateral movement** | SSH to internal hosts, remote file copy, network scans |
| **Command and control** | Connections to commonly abused ports, Tor, DNS over HTTPS, proxy tools, `socat` tunnels |
| **Exfiltration** | Uploads with `curl`, archiving before exfiltration, DNS exfiltration patterns |
| **Impact** | Cryptominers, bulk file deletion, disk wiping, service stops |

To see the coverage in action, run `make demo` and open the MITRE ATT&CK Coverage dashboard ([Quick Start](quickstart.md)).

## Writing your own rules

Add rules to `detection/config/rules/custom_rules.yaml`, for example:

```yaml
- rule: Detect Cryptocurrency Mining
  desc: Detect cryptocurrency mining processes
  condition: >
    spawned_process and
    proc.name in (xmrig, minerd, cpuminer)
  output: "Crypto miner detected (user=%user.name cmd=%proc.cmdline)"
  priority: CRITICAL
  tags: [cryptomining, mitre_impact]
```

Add a `mitre_<tactic>` tag so the event shows on the MITRE dashboard. Validate with `make test-rules`, then push the rules to fleet hosts with `make update-rules`. `examples/rules/` has more examples (`aws.yaml`, `k8s.yaml`, `web.yaml`), and [Sigma Rules](sigma-rules.md) covers converting community Sigma rules.

## Tuning already in the bundled rules

The bundled rules exclude these known-benign cases. Everything else in the same rules stays active.

- `/etc/passwd` is not in the sensitive-file list: it is world-readable, and routine account lookups made it the most frequent event by far. `/etc/shadow`, `/etc/sudoers` and `/etc/ssh/sshd_config` stay monitored.
- Pi-hole: writes below `/etc/pihole/`, and its downloads and copies through `/tmp` during gravity updates.
- Falcosidekick's healthcheck reads `/proc/net/tcp{,6}` instead of opening a connection without a certificate to the mTLS listener.
- Environment enumeration fires on `printenv` and reads of `/proc/*/environ`, not on plain `env`.
- The suspicious-port rule watches a fixed list of commonly abused ports (4444, 5555, 6666, 7777, 8888, 9999, 1337, 31337), not every high port.
- qBittorrent peer traffic from `qbittorrent-nox` is excluded from the suspicious-port rule; the same ports stay monitored for every other process.
- Unbound DNS replies from remote port 53 that land on one of those ports are excluded; other use of the ports stays.
- *Container Running as Root* fires only for the container's PID 1, not for every root healthcheck and child process.
- Local read-only VictoriaLogs queries (`curl --data-urlencode` against `http://127.0.0.1:9428/select/logsql/query`) are excluded; curl upload detection stays active elsewhere.
- Wazuh's `wazuh-modulesd` on the host reading `/etc/shadow` and `/etc/sudoers`, and updating `/etc/.pwd.lock`.
- `modprobe -n` / `--dry-run` and Docker's `modprobe -q -- veth…` probes; real module loading and removal stays Critical.

Before adding your own exclusions, see the tuning advice in [Configuration](configuration.md#authenticated-webhooks-and-agent-driven-triage).
